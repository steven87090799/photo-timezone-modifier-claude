# JPG／HEIC 保留驗證與壓縮清單更新（3.6.2）

日期：2026-10-05。Apple Silicon／macOS 27。本次修改延續 `codex/native-jpegli` 分支，未合併 main。

## 使用行為

- 同格式壓縮保留完整來源檔名，包括 `.JPG`、`.JPEG`、`.HEIC`、`.HEIF` 的原大小寫；互轉保留主檔名，只換成符合實際格式的副檔名。例如 `IMG_001.HEIC` → JPG 為 `IMG_001.jpg`。
- 批次及 ZIP 不再自動附加 `(2)`。遇到重複檔名或輸出資料夾已有同名檔案，在複製前拒絕並要求分批或換空資料夾。單張儲存視窗仍允許使用者明確自行輸入名稱。
- JPG／HEIC 保留原拍攝日期、三組時區偏移、GPS、相機／鏡頭／曝光、EXIF 方向及原 EXIF 像素尺寸欄位；MakerNotes、EXIF 縮圖及 PreviewImage 另核對二進位內容。無法可靠核對、關鍵 EXIF 變動時拒絕輸出。
- 原 ICC 存在且為支援的 RGB 描述檔時完整保留；XMP／IPTC 沿用既有複製及核對流程。格式無法保留 IPTC-IIM 時，結果會明確指出。
- 壓縮清單顯示相機、像素尺寸、ISO、光圈、快門、焦距、拍攝時間、拍攝時區、GPS 座標／高度、原始與輸出容量、減少／增加比例及容量差額、狀態、格式與處理進度。其他兩組時區及較長資訊可用懸浮說明查看，CSV 同時加入這些欄位。
- 外部 XMP 的 GPS 只讀取狀態並明示「未嵌入輸出」；壓縮頁沒有修改時區或 GPS 的控制，也不自動把 sidecar 嵌入照片。

### EXIF「不變」的核對界線

拍攝中繼資料保持原值；壓縮格式、色度取樣、檔案內部位址、位元排列等編碼結構必須隨新檔案改變，因此整個 EXIF 區塊不能宣稱二進位完全相同。已知 EXIF 欄位在 IFD0 與 ExifIFD 間合法移動可接受，值與重複項數量仍須匹配。FNumber 僅允許原有的微小十進位浮點表示誤差，不改動光圈的語義值。

## 實際找到並修正的問題

| 問題 | 修復與核對 |
| --- | --- |
| JPG／HEIC 原方向被正規化成 1 | 讀取實際 EXIF Orientation 並保留原值，不再改拍攝 EXIF 方向與尺寸 |
| HEIC 容器方向與 EXIF 方向不一致，僅保留標籤仍可能轉錯 | 先依 macOS 顯示結果解碼，再以原 EXIF 方向的反向旋轉／鏡像安排像素；HEIC 原生輸出同時設定容器方向；實際解碼畫面比對八種方向 |
| 批次同名自動改成 `(2)` | 預先拒絕重名，不悄悄改檔名 |
| 部分來源 Orientation 在 ExifIFD，複製到 IFD0 後誤判遺失 | 加入僅限這些已知 EXIF 欄位的合法位置匹配；不放寬 XMP 命名空間及重複值核對 |
| 清單只有名稱與大小，缺少拍攝資訊 | 匯入時使用可重用的唯讀 ExifTool 工作階段；清單與報表顯示基本資訊、時區、GPS、容量差額 |

## 驗證結果

1. 全套自動測試：**132 項通過、7 項選用測試未啟用**。包含真實 Sony ARW、43 張 JPEG 時區／GPS 流程及六種壓縮格式的既有回歸。未啟用的另有千張壓力測試及需要特定輸入／輸出目錄的校準；本次 JPG／HEIC 校準另行執行如下。
2. 新方向測試：JPG 與 HEIC，各 8 種旋轉／鏡像方向，再各輸出 JPG 與 HEIC，共 **32 份**。比對實際 macOS 顯示的像素尺寸與平均像素差、EXIF 原值、ICC、GPS／高度、時區、檔名、實際檔案 bytes、同名拒絕與來源不變。平均像素差門檻只用於偵測轉向錯誤，並非「肉眼無差異」畫質保證。
3. 桌面資料夾：43 張原始 JPG，以及先前由這些 JPG 轉出的 43 張 HEIC，雙向輸出，共 **172 份**通過。來源 86 份 SHA-256 前後相同；另以檔案系統讀回實際 bytes 與完整檔名，比對結果報表全部一致。照片全在本機處理，未上传。
