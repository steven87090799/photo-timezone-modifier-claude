# 3.6.1 修復與壓縮品質驗證（2026-10-05）

本次直接審查 `codex/native-jpegli` 的程式碼並修復，再執行測試。未合併 main、未替換本機安裝版。原始照片沒有修改或上傳；測試輸出留在桌面 testjpg/CompressionFix-20261005。

## 已修復問題

| 問題 | 修復與驗證 |
|---|---|
| 16 位元 PNG／JPEG XL 100 靜默降為 8 位元 | 原生 PNG 與 JXL 支援 16 位元整數 RGB／RGBA；直接複製整數樣本，測試透明與不透明影像逐樣本相同。浮點、非 RGB、預乘透明等無法保證無損的來源明確停止。其他有損格式降為 8 位元時提示。 |
| PNG 努力度提示與实际編碼不同 | UI 與引擎使用相同二次映射；16 位元 PNG 明示努力度由 macOS 決定。 |
| 縮圖放大被當成 100% 原圖比較 | 使用同座標、原生解析度 1024 像素裁切；100% 對應螢幕實體像素。裁切另複製小緩衝區，不保留整張原圖的資料提供者。 |
| 本機服務停止後，已接入連線仍殘留 | 追蹤已接受的連線並於停止時 shutdown；不再等待 40 秒接收超時。回歸測試驗證。 |
| JXL 色彩提示過時 | 提示來源 ICC 保留規則；無法可靠取得 ICC 時，無損輸出停止，不錯誤標記為 sRGB。 |
| 空清單與閒置壓縮頁仍保留 WebKit 引擎 | 選頁不載入引擎；僅 PNG 8 位元／WebP／AVIF 的工作按需載入。工作結束閒置 5 秒釋放整個 WebKit 與服務；再次工作可重建。JPEG／JXL／HEIF 原生輸出不需要 WebKit。 |
| HEIF 使用網頁橋接增加複製與資源 | 改直接呼叫 macOS ImageIO public.heic；實際輸出再次解碼、檢查尺寸、保留與驗證中繼資料。 |
| 退出時單次 ExifTool 可能成為孤立程序 | 集中登記 App 擁有的 ExifTool／ZIP 子程序；退出禁止新程序，TERM 後仍未停止則 KILL。用忽略 TERM 的子程序驗證清理與禁止延後啟動。 |
| 壓縮前後容量與批次減少比例可能失準 | 來源採寫入前固定檔案身分的實際 bytes，輸出在中繼資料完成後取實際檔案 bytes。單張、清單、CSV、Webhook 與批次使用相同值；批次只對同一組成功相片計算加權總比例。 |
| 不同格式共用品質導致錯用 JPEG 設定 | 各格式獨立記憶品質；JPEG 建議 86、HEIF 建議 70，保留既有自訂值，提供「建議品質」按鈕。 |
| JXL 重複輸出緩衝與工作執行緒偏多 | Swift 接管 C 緩衝區而不再完整複製，最多 4 個編碼執行緒；像素 chunk 與輸出階段檢查取消。 |
| 本機 libjxl 跟隨 Homebrew 最新版 | 固定 libjxl 0.12.0 原始碼提交与 SHA-256，從固定來源建置並打包動態函式庫；系統依賴版本納入快取識別。 |
| 打包顯示舊的資源版本 | 每次打包重新產生網頁資源版本與 BuildIdentity，診斷顯示實際提交、是否含未提交修改。 |
| 開發測試與打包同時重建 ExifTool，導致輸出失敗 | 實測發現並重現；加入準備鎖及有效固定版本快取重用，兩個並行準備期間檔案 inode／SHA 不變，43 張重新跑完。 |

## 品質選擇

沒有所有照片都適用的「完美」品質值。挑選 9 張涵蓋這批大小範圍的照片，測試 JPEG 6 種品質、HEIF 6 種品質；再用 43 張完整驗證預設值。以下百分比是同一组照片總 bytes 的減少比例，負值代表變大。

| JPEG 品質 | 容量減少 | SSIMULACRA2 中位數 | 最低分 |
|---|---:|---:|---:|
| 78 | 27.27% | 78.00 | 54.39 |
| 82 | 19.48% | 81.27 | 58.54 |
| 86 | 8.33% | 86.14 | 66.93 |
| 90 | -21.05% | 89.37 | 81.92 |
| 94 | -44.61% | 90.30 | 86.09 |
| 96 | -68.77% | 91.43 | 88.13 |

JPEG 採 86，保留正常品質的 4:2:0 與品質 90 以上的 4:4:4。另跑全 4:4:4 品質曲線：86 的中位數僅從 86.14 到 86.32，總容量反而增加 7.49%，因此不採用。此次沒有改成其他圖片容器，JPEG 仍是標準 .jpg。

| 原生 HEIF 品質 | 容量減少 | SSIMULACRA2 中位數 | 最低分 |
|---|---:|---:|---:|
| 60 | 27.85% | 76.98 | 70.39 |
| 70 | 15.77% | 81.14 | 76.43 |
| 80 | 3.63% | 83.87 | 81.13 |
| 86 | -8.27% | 85.73 | 84.02 |
| 90 | -41.92% | 88.90 | 86.11 |
| 94 | -94.68% | 90.29 | 86.75 |

HEIF 採 70 作為該格式的建議起點。HEIF 70 比 JPEG 86 更小，但畫質中位數也較低。在相近中位數下，JPEG 82（81.27 分、減少 19.48%）比 HEIF 70（81.14 分、減少 15.77%）更小；本次資料沒有證明 macOS HEIF 比 Jpegli 更有效，因此預設格式仍為 JPEG。

## 43 張完整測試

原始總大小 190,081,981 bytes。每張各輸出 JPEG 86 與 HEIF 70，共 86 份；以下包括已寫入的中繼資料。

| 格式 | 輸出 bytes | 總容量減少 | 畫質中位數／最低分 |
|---|---:|---:|---:|
| JPEG | 175,746,371 | 7.54% | 85.67 / 66.93 |
| HEIF | 160,471,048 | 15.58% | 81.12 / 70.45 |

86 份全部通過實際檔案大小、標準格式解碼、尺寸、既有 EXIF／日期／時區／GPS／ICC 核對。來源 43 張 SHA-256 前後一致。此批壓縮測試驗證保留既有 GPS；新增 GPS 與時區寫入由核心回歸测试另行驗證，不混同兩種成功。

容量公式：`(1 - 輸出總 bytes / 對應成功來源總 bytes) × 100%`。不平均每張百分比，也不把失敗來源列入分母。未輸出的預覽仍標示估算，不能當成實際檔案大小。

畫質比對：每份輸出取原圖與結果同座標的 3 個原生解析度 1024 像素裁切，共每格式 129 組，使用 SSIMULACRA2；沒有先縮小到 1200 像素。另目視查看最低 JPEG 分數照片的暗部裁切，結構與亮度接近、顆粒仍有差異。未逐張做人工盲測，沒有聲稱有損壓縮逐像素相同或完全看不出差別。數值只適用此次照片／此 Mac，不代表全部影像與其他 macOS 編碼器版本。

## 測試與退出

最後一輪核心 108 項、壓縮 30 項，共 131 項執行通過、7 項選用測試跳過。核心包含固定真實 Sony ARW 與桌面 43 張 JPEG 副本測試；1000 張壓力測試未跑。上面的實拍品質校準另開啟專用測試，完整 86 份成功。

一般退出實測：測試用 3.6.1 App 關閉後主程序消失，沒有殘留本 App 的 ExifTool 或本機監聽服務。子程序強制清理另由回歸測試驗證。閒置時仍開著視窗，App 自身必然需要記憶體，不能聲稱零資源；關閉最後視窗或退出才停止主程序。系統可能保留共用 WebKit 快取服務，不能當成本 App 仍在背景運作。進行檔案寫入時仍需先停止／完成，避免突然退出留下半份結果。

完整一般測試、精度／取消／WebKit 釋放測試與本機原生 HEIF 品質曲線均通過。沒有對外發送 Webhook；Webhook 由本機測試伺服器驗證。ON1／LR 真實編輯器匯入、Windows GUI、所有 macOS／相機型號未驗證。並行記憶體預估仍非 RSS 硬上限，不能宣稱 CPU 與記憶體已「最佳化到極致」。

第一次 43 張批次受到同時重建 ExifTool 影響而未完成，保留失敗紀錄；修復後的數字取自 default-quality-batch-final/results.json，不將部分成功當成完整結果。

原始證據：quality-curve/results.json、full-chroma-curve/results.json、default-quality-batch-final/results.json、exiftool-concurrent-preparation.json、exit-check/ 與 final-tests.log，均位於本次桌面輸出資料夾。
